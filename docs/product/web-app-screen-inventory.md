# Karamchari Web Application Screen Inventory

Derived from the implemented backend on 2026-06-10: 80 route groups, ~400 named endpoints across `src/Backend/Hosts/Karamchari.Api/BFF/*`, module DbContexts, integration events, and module READMEs. Every screen below is grounded in an existing API surface — nothing speculative. No UI design here; pages, purpose, users, actions, data, dependencies only.

Personas used throughout: **EMP** (Employee), **SUP** (Supervisor/Team Lead), **MGR** (Manager), **HR** (HR Admin), **PAY** (Payroll Admin), **FIN** (Finance/Billing), **REC** (Recruiter), **EXEC** (Executive), **CMP** (Compliance Officer), **SYS** (System Administrator), **OPS** (Platform Operations).

---

# Shell & Cross-Cutting

## Navigation Structure

### Login / Register / Session
Purpose: Authenticate against tenant; obtain JWT + refresh token.
Users: All.
Actions: Login, register, refresh, logout.
Data: Credentials, tenant binding (subdomain host).
APIs: `POST /api/identity/{register,login,refresh,logout}`.
Dependencies: Entry point for everything; tenant resolved from host.

### Global Search
Purpose: Cross-module people/talent/skill lookup.
Users: All (results permission-trimmed).
Actions: Search employees, talent, skills; navigate to detail pages.
Data: Employee summaries, skill matches, talent profiles.
APIs: `/api/v1/search/{employees,talent,skills}`.
Dependencies: Links into Employee Detail, Capability Profile.

### Notification Center
Purpose: Inbox of system notifications with unread badge; real-time via SignalR.
Users: All.
Actions: List inbox, mark read; deep-link to source records.
Data: NotificationMessage, unread count.
APIs: `/api/v1/notifications` (`Notifications.Inbox`, `UnreadCount`, `MarkRead`); hub `/hubs/notifications`.
Dependencies: Deep-links to every approval/detail page.

### Approvals Inbox (Unified)
Purpose: One queue for all pending approvals routed through the workflow engine.
Users: SUP, MGR, HR, PAY.
Actions: Approve, reject, view timeline.
Data: Pending approval items, decision timeline.
APIs: `/api/v1/approvals` (`Approvals.My`, `Timeline`, `Approve`, `Reject`).
Dependencies: Feeds from Leave, Reimbursement, Workflow definitions; links to source detail pages.

### My Profile
Purpose: Self view of identity, role, preferences, notification settings.
Users: All.
Actions: View profile, edit notification preferences.
Data: Identity claims, UserNotificationPreference.
APIs: identity + notifications preference endpoints.
Dependencies: None.

# Employee Self-Service (ESS / "Me")

## Navigation Structure

### My Dashboard
Purpose: Landing page: today's shift, attendance state, pending tasks, balances, announcements.
Users: EMP.
Actions: Quick check-in/out, jump to leave request, view announcements.
Data: Attendance session, leave balances, goals snapshot, announcements, recognition feed.
APIs: `/api/ess/*`, `/api/v1/me/*`, engagement feeds.
Dependencies: Aggregates Attendance, Leave, Goals, Engagement.

### My Attendance
Purpose: Personal attendance record and score.
Users: EMP.
Actions: Check-in/out, start/end break, view records, submit regularization.
Data: AttendanceSession, AttendanceRecord, AttendanceScore, anomalies affecting self.
APIs: `Attendance.CheckIn/CheckOut/Break.*`, `Attendance.Records.My`, `Attendance.Score.Me`, `Attendance.Regularization.Submit`.
Dependencies: Regularization flows into Approvals Inbox.

### My Leave
Purpose: Request and track leave; see balances.
Users: EMP.
Actions: Request full/half-day/hourly leave, submit, cancel, withdraw; view balance history.
Data: LeaveRequest, LeaveBalance (+history), LeaveType list, blackout periods.
APIs: `Leave.Request/HalfDay/Hourly/Submit/Cancel/Withdraw/My/Balance/BalanceHistory`.
Dependencies: Approval via workflow; balance affected by accrual jobs.

### My Payslips & Pay
Purpose: Payslip history, salary structure view, IT declarations.
Users: EMP.
Actions: View/download payslips, submit IT declaration.
Data: Payslip, EmployeePayrollResult, ITDeclaration, SalaryComponent breakdown.
APIs: `/api/payroll` employee-scoped + ESS endpoints.
Dependencies: Generated by payroll run completion.

### My Reimbursements
Purpose: Submit and track expense reimbursements.
Users: EMP.
Actions: Submit claim, list mine, view status.
Data: ReimbursementClaim, ExpenseCategory.
APIs: `Reimbursement.Submit/My/Get`.
Dependencies: Approval workflow; payout via payroll.

### My Loans & Advances
Purpose: Request loans, view schedule, pre-close.
Users: EMP.
Actions: Request, view amortization schedule, pre-close.
Data: EmployeeLoan, installments.
APIs: `Loan.Request/Get/Schedule/PreClose`.
Dependencies: Deductions appear in payslips.

### My Goals & Reviews
Purpose: Personal goal tracking and review tasks.
Users: EMP.
Actions: View goals/OKRs, update progress, complete review tasks, respond to feedback requests.
Data: Goal, Objective, ReviewTaskInboxItem, FeedbackRequest.
APIs: `Me.Goals`, `Me.ReviewInbox`.
Dependencies: Goal cycles activated by HR; reviews assigned by cycle.

### My Skills & Learning
Purpose: Capability profile, certifications, learning enrollments, recommendations.
Users: EMP.
Actions: View profile, add evidence, enroll/start/complete learning modules, view recommendations, browse mobility vacancies.
Data: CapabilityProfile, CertificationAchievement, LearningEnrollment, recommendations, MobilityVacancy.
APIs: `Capability.Profiles.GetMy`, `Capability.Learning.*`, `Me.Skills`.
Dependencies: Gap analysis vs Role Requirements; feeds career readiness.

### My Assets
Purpose: Assets currently assigned to me.
Users: EMP.
Actions: View list; acknowledge return at offboarding.
Data: Asset summaries by employee.
APIs: `Assets.ByEmployee`.
Dependencies: Asset Registry (admin side).

### My Helpdesk Tickets
Purpose: Raise and follow support tickets; search KB.
Users: EMP.
Actions: Raise ticket, comment, reopen; search/vote KB articles.
Data: SupportTicket (own), KbArticle.
APIs: `Helpdesk.Tickets.Raise/List/Get/Comment/Reopen`, `Helpdesk.KB.Search/Vote`.
Dependencies: Agent queue (Helpdesk module).

# MVP Web Application

Minimum coherent product per persona — P0 rows above, which form a closed loop (hire → attend → leave → pay):

**Employee (9):** Login, My Dashboard, My Attendance (check-in/out + regularization), My Leave (request + balance), My Payslips, Timesheet entry, Notification Center, Approvals participation (own request status), My Profile.

**Supervisor (6):** Manager Dashboard, Team Attendance Board, Regularization Queue, Team Leave Calendar & Approvals, Timesheet approval, Approvals Inbox.

**Manager (adds 3):** Review Inbox & Team Goals (read-only first), Talent Heatmap (read-only), Employee Detail (scoped subset).

**HR/Admin (12):** Employee Directory, Employee Detail, Employee Onboard Form, Org Structure Admin (departments/designations/locations minimum), Position assignment, Leave Type & Policy Admin, Attendance Policy Admin, Shift Definition Admin, Period Finalization, Report Center, Workflow Studio (publish the default leave/reimbursement workflows), Onboarding Cases (basic).

**Payroll Admin (7):** Payroll Cockpit, Run Console, Salary Structure Admin, Tax Config, Payslip Browser, Disbursement Center, IT Declaration Review.

**System Administrator (5):** Tenant Administration, Users & Roles, Workflow Studio (shared with HR), Data Migration Console, Ops Health.

MVP total: ~40 screens. Everything else (Recruitment, Succession, Intelligence, Platform Intelligence, Engagement, Billing/PSA, Forecasting) is P1/P2 expansion — the backend already supports all of it, so sequencing is a frontend decision only.
